# 数据库设计

> 本文给出物理库结构：52 张表（51 张业务表 + `seq_no` 发号器）、字段定义、索引、约束、状态枚举与初始化策略。核心遵循三条：三层数据（个体／群体／出现记录）在表层面就分开，不靠一个 type 字段混装；资金表只增不删，冲正留痕；所有状态字段配 CHECK 约束，非法值进不了库。

## 1 设计原则

**其一，三层数据物理分离。** 个体档案、群体档案、出现记录各用一张主表，字段按对象性质裁剪。合表会让"认养"无从挂靠，也会让"三只黄鼠狼"和"三只猫"被算成同一种数。三层共用 `base_point`（点位）与 `sys_file`（附件），但编号规则、统计口径、外键指向完全独立。

**其二，编号在库内唯一，不靠应用层自觉。** 业务编号（如 `CAT-2026-031`）既是主键的对外代理，也是用户口头引用与二维码的载体，因此建唯一索引，并由序列表发号，避免并发下重号。

**其三，资金只增不删。** `donation`、`expense`、`adoption_payment` 三张表禁止物理删除，更正通过新增一条 `reversal_of` 指向原记录的负向记录完成。数据库账号不给应用 DELETE 权限，从权限层面兜住。

**其四，所有状态字段有 CHECK 约束。** 状态值写错在应用层容易被忽略，落到库里就会变成"统计时查不到"的幽灵数据。CHECK 约束与《接口设计说明书》第 10 节枚举严格一致。

**其五，附件多态挂接。** 一张票据可能属于支出、也可能属于就诊或缴费，因此不为每类业务单独建附件表，而是用 `biz_type + biz_id` 挂接，索引建在这两列上。

## 3 核心表结构

类型按 MySQL 8 书写。所有表默认含 `id BIGINT AUTO_INCREMENT PRIMARY KEY`、`created_at`、`updated_at`、`created_by`，下文不再重复列出这三列。

### 3.1 animal（个体档案）

| 字段 | 类型 | 允许空 | 约束/默认 | 说明 |
|---|---|---|---|---|
| code | VARCHAR(20) | 否 | UNIQUE | 业务编号，`CAT-2026-031` |
| category | VARCHAR(8) | 否 | CHECK IN (CAT,DOG,OTHER) | 类别 |
| name | VARCHAR(32) | 是 | | 常用称呼，可空 |
| gender | VARCHAR(8) | 否 | CHECK IN (MALE,FEMALE,UNKNOWN) | 性别 |
| color | VARCHAR(16) | 否 | | 花色，取自字典 |
| estimated_age | TINYINT | 是 | CHECK BETWEEN 0 AND 25 | 估计年龄 |
| features | VARCHAR(255) | 否 | | 识别特征 |
| point_id | INT | 否 | FK base_point | 常驻点位 |
| status | VARCHAR(16) | 否 | CHECK IN (ON_CAMPUS,TREATING,HOSPITALIZED,TO_RELEASE,RELEASED,ADOPTED,MISSING,DECEASED)，默认 ON_CAMPUS | 当前状态 |
| neutered | TINYINT(1) | 否 | 默认 0 | 是否绝育 |
| neutered_at | DATE | 是 | | 绝育日期 |
| adopted | TINYINT(1) | 否 | 默认 0 | 是否在认养中 |
| cover_file_id | VARCHAR(24) | 是 | FK sys_file | 封面图 |
| internal_note | TEXT | 是 | | 内部备注，不对外 |

关于 `adopted` 冗余字段：它可由 `adoption` 表派生，但列表查询与筛选高频使用，故冗余保留，由缴费入账与终止两处事务同步维护。**只允许这两个入口修改**，其他路径写该字段视为缺陷。

## 5 实体关系

三条主线，互不交叉，共用点位与附件：

**个体线**：`animal` 1—N `health_record`、1—N `visit`、1—N `animal_status_log`、1—N `animal_change_log`；`adoption` N—1 `animal`、N—1 `sys_user`；`adoption` 1—1 `adoption_payment`（同一周期内）。资金链是三张表串起来的：`expense` N—1 `project`，`expense` N—1 `animal`，`expense` N—1 `visit`（可空）——这条链让"这笔钱救了哪只猫、对应哪次就诊"可以一条 SQL 追到底。

**群体线**：`animal_group` 1—N `sighting`；`sighting` N—1 `base_point`。群体合并时 `merged_from` 记录被并入编号，历史目击不做数据迁移，查询时用 `group_id` 联合 `merged_from` 展开，保证可追溯。

**物种线**：`base_species` 1—N `occurrence`；`base_species` 1—N `animal_group`。出现记录只指向物种与点位，不指向个体或群体，这是三层隔离的关键约束。

认养关系是"多对多但带时间约束"：一名学生可有多条认养记录（受 ≤2 限制），一只动物同一时间只能有一条 `ACTIVE`。因此不能只靠外键，必须由 `uk_adoption_active` 唯一索引加服务层区间校验共同保证。

## 6 约束与索引策略

| 类型 | 内容 | 落地 |
|---|---|---|
| 唯一性 | 档案编号、群体编号、认养单号、项目编号、捐赠编号、支出编号、工单编号 | 各表唯一索引 |
| 状态一致性 | 状态字段只能取枚举值 | CHECK 约束，与应用枚举同源 |
| 业务一致性 | 支出必须关联项目与动物；超额支出必须双签 | NOT NULL + CHECK |
| 时序 | 支出时间 ≥ 项目开始；入账时间 ≥ 凭证上传；放归时间 ≥ 手术时间 | 服务层校验 + 异常日志 |
| 只增不删 | 资金三表禁用 DELETE | 数据库账号权限收回 |
| 软删除 | 档案、项目、公告 | `deleted` 标记 + 全局查询过滤 |

索引策略按查询频次定，不追求全覆盖：

| 索引 | 支撑查询 |
|---|---|
| `idx_animal_status_point(status, point_id)` | 档案列表按状态与点位筛选 |
| `idx_donation_project_status(project_id, status)` | 项目进度的已入账合计 |
| `idx_expense_project_status(project_id, status)` | 项目余额与待复核队列 |
| `idx_order_status_deadline(status, deadline_at)` | 超时工单高亮 |
| `idx_occurrence_species_point(species_id, point_id, occurred_at)` | 物种点位季节分布 |
| `idx_log_actor_time(actor_id, created_at)` | 日志按人按时间检索 |

## 7 视图与统计口径

统计不直接查明细表，统一走三个视图，保证页面数字与文档口径一致：

| 视图 | 定义要点 | 对应指标 |
|---|---|---|
| v_animal_overview | 按 status 分组计数，排除 `deleted=1` 与 `DECEASED`（绝育率分母） | 在册个体数、状态分布、绝育率 |
| v_group_overview | 按 status 分组，sum(size_min)/sum(size_max) 给区间 | 群体数、规模区间 |
| v_project_fund | 项目维度 union 入账与已复核支出，冲正按净额 | 已筹、已支出、结余 |

一条硬规则：`v_project_fund` 里 `结余 = 已筹 − 已支出` 必须恒成立。若出现负数，说明有绕过复核的支出写入了库，属于严重缺陷，接口层应拒绝返回并告警。

## 8 初始化与演进

**发号器。** 编号不用自增主键拼接，而是用 `seq_no` 表按"类型 + 年份"计数，`SELECT ... FOR UPDATE` 取号后 +1，保证不重号也不跳号。答辩演示时若需重置，只清空业务表并重置 `seq_no`。

**迁移脚本。** 所有 DDL 放 `/db/migration`，命名 `V1__init.sql`、`V2__add_tnr.sql` 递增，禁止手工改库。每份脚本必须可重复执行（`IF NOT EXISTS`）并在测试库跑通后再合入。截至 v1.7 已执行到 `V22__p2_followup_shift_benefit_care.sql`，主库与测试库表数均为 52。

**种子数据。** 与演示数据分离：`seed_dict.sql` 只放字典与角色权限（必装），`seed_demo.sql` 放 200 只档案、12 个项目、1200 笔捐赠、5 组群体（演示用，可一键清空）。

**备份。** 每日 02:30 全量备份，保留 30 天；资金表每周额外做一次逻辑导出（csv），离线保存一份，防止误操作导致账目丢失。

## 9 P2 收口增补（V22）

`V22__p2_followup_shift_benefit_care.sql` 新增 8 张表，全部沿用 `id / created_at / updated_at / created_by` 公共列，不改变既有列语义。新增后物理表总数为 52。

### 9.1 领养交接与回访

| 表 | 关键字段 | 约束与索引 |
|---|---|---|
| animal_handover | handover_no、animal_id、animal_code、adopter_name、contact、guardian_consent、residence_note、status、adopted_at | `uk_handover_no`；`idx_handover_animal(animal_id,status)`；status ∈ ACTIVE/RETURNED/CLOSED；animal_id 外键 |
| handover_followup | handover_id、seq_no、due_date、status、result、note、completed_at、operator_id | `uk_followup_handover_seq(handover_id,seq_no)`；`idx_followup_due(status,due_date)`；seq_no 1–3；result ∈ NORMAL/ABNORMAL |

回访日期在建交接单时由 `adopted_at + 7/30/90 天` 固化，不随动物或认养单变更。回访结果只允许正常/异常两态，避免出现第三套健康结论。

### 9.2 志愿排班与缺勤

`volunteer` 增加 `absence_streak`（连续缺勤次数，默认 0）与 `suspended_at`（暂停接单时间）。

| 表 | 关键字段 | 约束与索引 |
|---|---|---|
| volunteer_shift | shift_no、title、point_id、shift_date、start_time、end_time、capacity、booked、status | `uk_shift_no`；`idx_shift_week(shift_date,status)`；end_time > start_time；capacity 1–100；status ∈ OPEN/CLOSED/CANCELED |
| volunteer_shift_signup | shift_id、user_id、signed_at、checkin_at、absent、hours | `uk_shift_signup_user(shift_id,user_id)`；`idx_shift_signup_absent(user_id,absent)`；shift_id、user_id 外键 |
| volunteer_appeal | user_id、reason、status、reviewer_id、review_reason、decided_at | `idx_appeal_user(user_id,status)`；status ∈ PENDING/APPROVED/REJECTED |

连续缺勤按“签到即清零”的口径累计，不设自然周窗口；第 3 次缺勤在同一事务内把 `volunteer.status` 置为 `SUSPENDED` 并投递 `VOLUNTEER_SUSPEND`。申诉通过仅恢复 `ACTIVE` 并清零 `absence_streak`，不追溯已记缺勤的班次。

### 9.3 认养人专属权益

| 表 | 关键字段 | 约束与索引 |
|---|---|---|
| adoption_post | adoption_id、author_id、title、content | `idx_post_adoption(adoption_id,created_at)`；adoption_id、author_id 外键 |

### 9.4 疫苗与用药计划

| 表 | 关键字段 | 约束与索引 |
|---|---|---|
| care_plan | plan_no、animal_id、type、item_name、dosage、plan_date、status、source_visit_id、result、completed_at、operator_id、reminded_at、note | `uk_care_plan_no`；`idx_care_plan_animal(animal_id,status,plan_date)`；`idx_care_plan_due(status,plan_date)`；type ∈ VACCINE/MEDICATION；status ∈ PLANNED/DONE/CANCELED |
