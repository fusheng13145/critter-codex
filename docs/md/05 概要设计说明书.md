# 概要设计

> 本文承接需求与功能分析，给出系统的物理形态：分层、包结构、关键流程的时序、事务边界、定时任务、安全与部署。目标只有一个——让三个人各自开工时不必反复开会确认"这个逻辑放哪一层"。

## 1 架构选型与理由

采用单体分层架构，前后端分离部署。这不是技术保守，而是与规模、人力、评审要求三者匹配的结果。

| 维度 | 现状 | 结论 |
|---|---|---|
| 用户规模 | 5000 注册、300 日活、峰值 50 并发 | 单体足够，微服务的运维成本反而吃掉开发时间 |
| 团队 | 3 人，10 周 | 拆分服务等于给三个人加四套部署脚本 |
| 业务耦合 | 认养、资金、档案强耦合（一笔支出同时关联项目与动物） | 跨库事务会引入分布式一致性，单体下一个本地事务即可 |
| 课程要求 | 需要展示分层清晰、事务与状态机 | 单体分层反而更容易讲清楚"规则在哪一层" |

技术栈：Spring Boot 3.x + MyBatis-Plus + MySQL 8 + Redis（缓存字典与令牌黑名单）+ Vue 3 + Vite + Pinia + Element Plus。附件存本地目录（生产可切对象存储），定时任务用 Spring `@Scheduled`。

## 2 分层与职责

四层加两个横切。层的边界是硬约束：上层可调下层，下层不得反向依赖上层；横切通过注解与拦截器织入，不侵入业务代码。

| 层 | 包 | 职责 | 不允许做的事 |
|---|---|---|---|
| 接口层 | `controller` | 参数校验、权限注解、DTO 转换、HTTP 语义 | 不写业务判断，不直接调 Mapper |
| 应用层 | `service` | 编排用例、事务边界、状态机推进 | 不拼接 SQL，不处理 HTTP |
| 领域层 | `domain` | 实体、枚举、状态迁移表、领域校验 | 不依赖 Spring Web |
| 数据层 | `mapper` | 单表 CRUD 与视图查询 | 不含业务规则 |
| 横切 | `support` | 鉴权、异常、日志、上传、字典缓存 | 不写具体业务 |

```
com.qywl
├── controller/            // 按域分包：auth, user, archive, adopt, fund, rescue, content, stats
├── service/
│   ├── archive/           // 档案域应用服务
│   ├── adopt/             // 认养域
│   ├── fund/              // 资金域
│   └── support/           // 鉴权、字典、文件、消息
├── domain/
│   ├── model/             // 实体
│   ├── enums/             // 状态与类型枚举（与接口文档第 10 节同源）
│   └── statemachine/      // 迁移表定义与 TransitionEngine
├── mapper/
├── support/
│   ├── security/          // JWT、权限注解、字段脱敏
│   ├── exception/         // BusinessException、全局处理器
│   ├── file/
│   └── job/               // 定时任务
└── config/
```

## 3 关键设计决策

**决策一：状态机表驱动。** 五类对象的状态迁移定义在一个 `Map<ObjectType, List<Transition>>` 里，`TransitionEngine.fire(entity, event, operator)` 负责查表、校验权限、执行迁移、写日志、发消息。业务代码只写"发什么事件"，不写"从 A 能不能到 B"。好处有三：新增状态只改表；测试用例可由表批量生成；非法迁移的报错信息天然统一（返回当前状态与允许集合）。

**决策二：资金余额用行锁算，不用乐观锁重试。** 支出登记时对 `project` 行 `SELECT ... FOR UPDATE`，在同一事务内算余额并插入支出。并发下乐观锁会频繁失败重试，用户体验差且日志噪音大；行锁的争用只集中在单个项目上，代价可接受。

**决策三：冗余汇总字段由固定入口维护。** `project.raised_amount`、`project.spent_amount`、`animal.adopted` 都是冗余，但只允许两个事务（入账、复核）与一个事务（缴费入账、终止）修改。为此在 Mapper 层不加通用 update 方法，只暴露 `increaseRaised()`、`increaseSpent()` 这类语义方法，从代码结构上防止乱改。

**决策四：附件两步上传。** 先 `POST /files` 拿 `fileId`，再挂业务。好处是同一张票据可被就诊与支出共用，审核状态只有一份，去重也容易。代价是可能产生孤儿文件，用每日清理任务回收 7 天未被引用的 `fileId`。

**决策五：字段级脱敏在序列化层做。** `@Sensitive(field = PHONE, roles = {ANIMAL_ADMIN})` 注解标在 DTO 字段上，序列化时按当前用户角色决定是否输出。不在 SQL 里 `IF(role=...)` 拼字段，避免同一个查询出现多个版本难以维护。

## 4 关键流程时序

### 4.1 云认养申请到生效

```
学生            前端              AdoptionService        AnimalService      消息
 |  申请           |                     |                     |              |
 |--------------->|  POST /adoptions    |                     |              |
 |                |-------------------->|                     |              |
 |                |                     | 1 校验动物可认养     |              |
 |                |                     |-------------------->|              |
 |                |                     | 2 锁定动物行         |              |
 |                |                     |   查生效关系(唯一索引)|              |
 |                |                     | 3 查本人 ACTIVE 数≤2 |              |
 |                |                     | 4 写 adoption(PENDING_AUDIT)        |
 |                |<--------------------|                     |              |
 |                | 待审核单             |                     |              |
 |  管理员审核      |  PUT /adoptions/{no}/audit                |              |
 |                |-------------------->| 状态→PENDING_PAYMENT |              |
 |                |                     |------------------------------>  推送待缴费 |
 |  线下转账+上传凭证| PUT /adoptions/{no}/payment (事务)        |              |
 |                |-------------------->| ① 写 payment         |              |
 |                |                     | ② adoption→ACTIVE    |              |
 |                |                     | ③ animal.adopted=1   |              |
 |                |                     | ④ 写 sys_log         |              |
 |                |                     | ⑤ 投递消息           |              |
 |                |<--------------------| 证书编号 + 起止日期   |              |
```

要点：第 2 步的"锁动物行"与第 3 步的"计数"在同一事务内；第 ③ 步改动物状态必须走 `AnimalService.changeStatus`，不得直接 update，否则状态日志缺失。

### 4.2 支出登记与复核

```
管理员A           FundService                  Project(行锁)      复核人B
 |  POST /expenses    |                              |               |
 |------------------->| 开启事务                      |               |
 |                    | SELECT ... FOR UPDATE ------>|               |
 |                    | balance = raised - spent     |               |
 |                    | if amount > balance → 40103  |               |
 |                    | INSERT expense(PENDING_REVIEW)|              |
 |                    | COMMIT                        |               |
 |                    |                               |               |
 |  PUT /{no}/review  | amount ≤ 500 → APPROVED       |               |
 |------------------->| spent += amount; log          |               |
 |                    |                               |               |
 |                    | amount > 500 → FIRST_APPROVED |               |
 |                    |<------------------------------|               |
 |                    |  B 再调 review → APPROVED     |               |
 |                    |  if reviewer == handler → 40104               |
```

要点：超额支出分两次调用而非一次传两个复核人，因为现实中两人不在同一台电脑前；第二次调用才累加 `spent`，保证"未复核不计支出"。

### 4.3 上报转工单

```
学生          ReportService      OrderService       AnimalService     消息
 | 上报 ------->|                   |                  |              |
 |             | 写 report(PENDING)|                  |              |
 |             | 同点位24h去重提示  |                  |              |
 | 管理员受理 -->|------------------>| 建工单(deadline=+24h)          |
 |             |                   | 关联档案/或提示建档 |              |
 |             |                   |----------------->| 建档或关联    |
 |             |                   |--------------------------------> 推送给学生 |
 | 定时扫描 ----|------------------>| 超24h未受理 → TIMEOUT 并高亮     |
```

### 4.4 结项公示

结项是"锁账"动作：先校验是否存在 `PENDING_REVIEW`/`FIRST_APPROVED` 的支出（有则 40105 拒绝），再把项目置 `PENDING_SETTLE`，提交结项报告后置 `SETTLED` 并生成公示记录。公示发布后 `project_settlement` 行只允许追加 `append_note`，正文与金额字段在数据库层加 `CHECK` 之外的约束——通过"只暴露 append 接口，不暴露 update 接口"实现。

## 5 定时任务

四个任务，全部幂等、可重跑，失败不阻塞主流程：

| 任务 | 频率 | 逻辑 | 失败处理 |
|---|---|---|---|
| 认养到期提醒 | 每日 02:00 | 扫 `end_date = today+7` 且 `ACTIVE`，发提醒；扫 `end_date < today` 转 `EXPIRED` 并释放动物 | 记日志，次日重跑（幂等） |
| 工单超时 | 每小时 | `PENDING` 且 `deadline_at < now` → `TIMEOUT`，待办高亮 | 同上 |
| 群体失活 | 每日 03:00 | `ACTIVE` 且 `last_seen_at < now-60d` → `UNCONFIRMED` | 同上 |
| 孤儿文件清理 | 每日 04:00 | 7 天未被任何业务表引用的 `sys_file` 标记待删 | 仅标记，不物理删 |

所有任务用 `sys_log` 记录执行结果（`action='JOB_xxx'`），便于答辩时演示"系统确实在跑"。

## 6 异常与错误处理

统一异常体系三层：

| 异常 | 来源 | 处理 |
|---|---|---|
| `BusinessException(code, message, data)` | 服务层主动抛 | 全局处理器转 code/message/data，HTTP 200 |
| `StateTransitionException` | 状态机 | 转 30402/30602，附当前状态与允许集合 |
| 未捕获异常 | 任意 | 转 50001，日志记全栈 + requestId，响应不含堆栈 |

三条纪律：**业务异常必须带码**，禁止 `throw new RuntimeException("失败")`；**错误信息面向用户**，写"项目余额不足，尚差 200.00 元"而不是"insufficient balance"；**日志与响应分离**，日志可以有堆栈和 SQL，响应只给人看的话。

参数校验用 `@Valid` + 自定义校验注解，错误统一收敛为 30301 并按字段聚合，前端一次标红所有问题，不必逐条试错。

## 7 安全设计

| 面 | 措施 |
|---|---|
| 认证 | JWT 双令牌；访问令牌 2 小时；刷新令牌 httpOnly Cookie；注销入黑名单（Redis，TTL 同令牌有效期） |
| 授权 | 接口注解 + 服务层二次校验；系统管理员无业务审核权，白名单硬编码 |
| 字段 | `@Sensitive` 序列化脱敏；手机号 AES 加密存储；公开页不含任何联系方式 |
| 输入 | 参数校验、MyBatis 预编译、富文本白名单过滤、上传 MIME 与扩展名双校验并重编码 |
| 文件 | 存储路径 UUID 化、禁止目录穿越、票据不提供公开直链（经鉴权接口取流） |
| 审计 | 资金与档案操作全量写 `sys_log`，含前后值与 IP；日志只读 |
| 传输 | 全站 HTTPS；生产禁 DEBUG 日志；错误响应不回显 SQL |

## 8 性能设计

按 NFR-01/NFR-02 的口径，做四件事即可，不必过度优化：

1. **分页强制**：所有列表接口必须分页，单页上限 100，禁止 `select *` 全表返回。
2. **字典与点位缓存**：`sys_dict`、`base_point`、`base_species` 启动加载进 Redis，变更时失效；这三张表读远多于写。
3. **索引对齐查询**：第 4 节数据库文档给出的六个索引对应六类高频查询，新增查询必须能命中已有索引，否则先加索引再上线。
4. **统计走视图**：总览类接口查视图或定时物化，不在列表接口里实时 `sum` 明细。

首年数据量下（档案 200、捐赠 2000、日志 4 万），上述设计足以满足"列表 1 秒内、页面 2 秒内"的要求。

## 10 与需求的对应关系

| 需求项 | 设计落点 |
|---|---|
| 三层数据模型 | `animal` / `animal_group` / `occurrence` 三表 + 共用 `base_point`、`sys_file` |
| 四类状态机 | `domain/statemachine` 迁移表 + `TransitionEngine` |
| 资金双向可追溯 | `donation` / `expense` 双表 + `expense.animal_id` 强制 + 行锁余额校验 |
| 权限与合规分层 | `@Sensitive` + 服务层白名单 + 联系方式加密 |
| 只增不删 | 数据库账号收回 DELETE + 冲正字段 `reversal_of` |
| 24 小时受理 | 工单 `deadline_at` + 每小时扫描 |
| 二维码档案页 | 公开路由 `/p/{code}` + 字段白名单 DTO |

## 11 设计遗留与后续

三处已知的取舍，答辩时如被问到可直接说明：

1. **不做分布式事务**：单体已足够，若未来资金模块独立部署，需引入本地消息表做最终一致。
2. **附件存本地**：换机器需搬目录；生产建议切对象存储，接口层已抽象 `FileStorage`，替换不动业务代码。
3. **消息走站内**：不发短信与邮件（需求明确不接第三方通道），重要提醒靠登录后的消息中心，接受"用户不登录就收不到"的局限。
