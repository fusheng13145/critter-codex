# T2.3 工单看板与流转说明

## 1 接口

| 方法/路径 | 鉴权 | 说明 |
|---|---|---|
| `GET /api/v1/orders` | `ANIMAL_ADMIN` / `SYSTEM_ADMIN` | 工单列表；`status` 逗号分隔、`type`、`overdue`、`page`、`size` |
| `GET /api/v1/orders/{no}` | 登录 | 工单详情、来源上报与时间线 |
| `PUT /api/v1/orders/{no}/status` | `ANIMAL_ADMIN` | 状态流转；请求 `targetStatus` 必填，`note`/`reason`/`handlerId` 按事件使用 |

## 2 列表口径

- 按 `created_at DESC` 排序，`overdue` 服务端计算，不落库。
- `overdue=true`：`status=TIMEOUT`，或 `status=PENDING` 且 `deadline_at < now`。含义是"24 小时受理时限已过"；已受理工单即使处置超过 24 小时，不算受理超时。
- `overdue=false`：排除上述组合；`CLOSED` 工单不参与超时判断。
- 来源上报、点位按 `report_id` 批量回查；列表不返回上报描述/照片/联系方式，避免看板接口扩大敏感字段面。

**当前数据形态**：`POST /reports` 创建上报时即生成一条 `PENDING` 工单；`POST /reports/{id}/accept` 复用该工单并按 `ACCEPT` 迁移为 `PROCESSING`。`OrderTimeoutJob` 每小时把 `PENDING` 且 `deadline_at < now` 的工单置为 `TIMEOUT`，因此正常业务数据会同时存在 `PENDING / PROCESSING / TIMEOUT / CLOSED`。

## 3 详情与时间线

详情返回：

- 工单：`orderNo`、`status`、`createdAt`、`deadlineAt`、`acceptedAt`、`acceptorId`、`handlerId`、`disposeNote`、`closeReason`；
- 来源上报：`reportId/reportNo/type/pointId/pointName/description/photos`；
- 档案：`animalId/animalCode`；
- `allowed`：当前状态允许的目标状态，供前端禁用按钮；不包含 `TIMEOUT`；
- `timeline`：`sys_log` 中 `biz_type=RESCUE_ORDER`、`biz_id=工单号`、`result=SUCCESS` 的记录，按时间升序。

时间线不另建事件表，直接复用操作日志。受理日志 `REPORT_ACCEPT` 的 `before` 是上报 `PENDING`、`after` 是 `PROCESSING`，因此工单时间线第一条能还原"受理并转工单"。后续流转写：

| 事件 | action | 中文展示 |
|---|---|---|
| `ACCEPT` | `ORDER_ACCEPT` | 受理并指派处置人 |
| `DISPOSE_DONE` | `ORDER_DISPOSE` | 完成处置，转待回访 |
| `CANNOT_DISPOSE` | `ORDER_CLOSE` | 无法处置，关闭工单 |
| `REVISIT_OK` | `ORDER_REVISIT_OK` | 回访正常，关闭工单 |
| `REVISIT_ANOMALY` | `ORDER_REVISIT_ANOMALY` | 回访异常，转回处理中 |

## 4 流转规则

- 事件由 `targetStatus` 反查 `StateMachines.order()` 迁移表得到，不在服务层写 if-else。
- `PENDING -> PROCESSING`（`ACCEPT`）：写 `accepted_at`、`acceptor_id`，`handlerId` 未传时沿用原处置人或当前管理员。
- `PROCESSING -> TO_REVISIT`（`DISPOSE_DONE`）：`note` 必填，写 `dispose_note`。
- `PROCESSING -> CLOSED`（`CANNOT_DISPOSE`）：`reason` 必填且 ≤255 字，写 `close_reason`。
- `TO_REVISIT -> CLOSED`（`REVISIT_OK`）：`reason` 可空，空时默认"回访确认恢复良好"。
- `TO_REVISIT -> PROCESSING`（`REVISIT_ANOMALY`）：`note` 必填，写回访异常说明。
- `TIMEOUT -> PROCESSING`（`ACCEPT`）：允许重新受理，刷新 `accepted_at`。
- `TIMEOUT` 不允许手工触发，只能由扫描任务执行；接口直接回 30602。
- 终态 `CLOSED` 无 `allowed`，任何再次流转回 30602。

## 5 错误码

| 码 | 触发 |
|---|---|
| 30301 | 目标状态缺失、处置说明/回访异常说明为空、关闭原因超长 |
| 30303 | `status`/`type`/`targetStatus` 枚举非法 |
| 30401 | 关闭原因为空 |
| 30410 | 工单不存在 |
| 30602 | 迁移表无此目标、手工触发 TIMEOUT、终态再流转 |

非法迁移抛 `StateTransitionException`，`data={current,target,allowed}`，`allowed` 已过滤 `TIMEOUT`。

## 7 本轮边界

1. **超时扫描已闭环**：见 §8；本轮之后 `PENDING` 工单会按 24 小时时限自动转 `TIMEOUT`。
2. **学生进展通知未接**：工单流转只写状态与审计，站内消息仍依赖 C 的消息通道。
3. **并发流转无乐观锁**：`rescue_order` 表没有 version 字段，两个管理员同时流转时后写覆盖先写；当前用状态机保证单次合法性，后续可补 `@Version` 或条件更新。
4. **处置人未校验存在性**：`handlerId` 只做透传，未校验用户是否存在；等 D1 用户查询接口稳定后补。

## 8 超时扫描闭环（2026-11-21）

| 项 | 落地 |
|---|---|
| 调度 | `CritterBackendApplication` 加 `@EnableScheduling`；`OrderTimeoutJob` 默认启动后 60 秒首次执行，之后每小时一次，配置键 `critter.jobs.order-timeout` |
| 候选 | `rescue_order.status=PENDING AND deadline_at < now` |
| 迁移 | 经状态机 `PENDING --TIMEOUT--> TIMEOUT`；用 `LambdaUpdateWrapper` 条件更新 `id + status=PENDING`，多实例下只有一个成功 |
| 审计 | 成功的每条写 `sys_log`：`action=ORDER_TIMEOUT`、`biz_id=orderNo`、`after_json` 含工单号与截止时间 |
| 再受理 | `TIMEOUT` 工单被 `POST /reports/{id}/accept` 复用，经 `TIMEOUT --ACCEPT--> PROCESSING` 迁移，刷新 `accepted_at`，不再新建工单 |
| 验证 | 回填 `deadline_at` 为过去时间后，扫描任务将工单置 `TIMEOUT` 并写审计；再次受理成功转 `PROCESSING` |

扫描结果结构 `OrderTimeoutScanResult { candidates, timedOut }`，供日志与后续监控消费；当前无 HTTP 触发接口，只由调度线程调用。
