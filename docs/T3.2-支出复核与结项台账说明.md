# T3.2—T3.5 支出复核、结项公示与逐笔台账说明

> 状态：已完成（2026-11-21）。新增迁移 `V14__expense_double_sign_stage.sql`，`critter_codex_dev` 已应用至 V14；金额单位全部为整数分。

## 1 交付范围

| 能力 | 接口 | 落地 |
|---|---|---|
| 支出登记 | `POST /api/v1/expenses` | 锁项目行后算余额，落 `PENDING_REVIEW`，不动 `spent_amount` |
| 支出列表 | `GET /api/v1/expenses` | 按状态、项目筛选，分页，仅 `ANIMAL_ADMIN` |
| 支出复核 | `PUT /api/v1/expenses/{expenseNo}/review` | ≤50000 分一签；>50000 分两签；仅第二签落 `APPROVED` 并累加项目 `spent_amount` |
| 逐笔台账 | `GET /api/v1/ledger` | 收入取 VERIFIED 捐赠、支出取 APPROVED 支出，合并倒序；管理员只读 |
| 结项提交 | `PUT /api/v1/projects/{projectNo}/settle` | 校验未复核支出、报告、结余去向；项目转 `SETTLED` |
| 结项公示 | `GET /api/v1/projects/{projectNo}/settlement` | 公开只读，返回收支、结余、报告与附件 |

不在本轮范围：支付/退款、支出删除、结项修订、台账导出。

## 2 支出状态机

```text
登记 ──> PENDING_REVIEW
            │
            ├─ 金额 ≤ 50000 分：一名管理员通过 ──> APPROVED
            ├─ 金额 >  50000 分：第一签 ──> FIRST_APPROVED ──> 第二签 ──> APPROVED
            └─ 任一复核人驳回 ──> REJECTED
```

- 登记人不得复核自己登记的支出（40104）；第二签不得与第一签同人（40104，message 为“第二签不得与第一复核人相同”）。
- 只有 `APPROVED` 才更新 `project.spent_amount` 与台账；`PENDING_REVIEW`、`FIRST_APPROVED`、`REJECTED` 均不计支出。
- 第一签与第二签分别记录 `first_reviewer_id`、`second_reviewer_id`；`review_reason` 保存最近一次意见。

## 3 余额与并发

登记时在同一事务内：

1. `SELECT ... FOR UPDATE` 锁 `project` 行；
2. `balance = project.raised_amount − sum(APPROVED 支出)`；
3. `reserved = sum(PENDING_REVIEW + FIRST_APPROVED 支出)`；
4. `available = balance − reserved`；
5. `amount > available` 返回 `40103`，`data` 带 `projectBalance / reserved / requested / gap`。

这样可避免两笔待复核支出把同一笔余额重复占用；第二签再次校验余额，防止复核期间余额被其他支出消耗。

## 4 数据库约束修复（V14）

`V1__init.sql` 的 `ck_expense_double_sign` 原要求大额支出在 INSERT 时同时具备两名复核人，但登记阶段两人必然为空，导致 >500 元支出永远无法登记。V14 改为：

```sql
CHECK (status <> 'APPROVED'
       OR amount <= 50000
       OR (first_reviewer_id IS NOT NULL AND second_reviewer_id IS NOT NULL))
```

约束只守住“最终通过的大额支出必须双签”，不阻断登记与第一签。

## 5 接口示例

### 5.1 登记

```http
POST /api/v1/expenses
Authorization: Bearer <ANIMAL_ADMIN token>
```

```json
{
  "projectNo": "PRJ-2026-007",
  "animalCode": "CAT-2026-001",
  "purpose": "绝育手术费",
  "amount": 60000,
  "payee": "示例动物医院",
  "occurredAt": "2026-11-21T10:00:00+08:00",
  "voucherFileIds": ["F20261121001"]
}
```

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "expenseNo": "EX202611210001",
    "status": "PENDING_REVIEW",
    "note": "支出已登记，待管理员复核后计入项目支出"
  }
}
```

约束：项目与动物必填；用途 ≤32 字、收款方 ≤64 字；发生时间不早于项目开始日期；票据 1—10 张；金额 1—10000000 分。

### 5.2 复核

```http
PUT /api/v1/expenses/EX202611210001/review
```

```json
{ "decision": "APPROVE", "reason": "票据与金额一致" }
```

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "expenseNo": "EX202611210001",
    "status": "APPROVED",
    "needSecondReview": false,
    "project": { "projectNo": "PRJ-2026-007", "raised": 100000, "spent": 60000, "balance": 40000 },
    "message": "支出已复核通过并计入项目支出"
  }
}
```

驳回时 `decision=REJECT`，`reason` 至少 5 字。

## 6 台账口径

- 收入：`donation.status=VERIFIED`，按 `verified_at` 归入区间，金额为 `amount`。
- 支出：`expense.status=APPROVED`，按 `occurred_at` 归入区间，金额为 `amount`。
- 合并后按发生时间倒序；同一时间按单号稳定排序。
- `summary.income / expense / balance / donationCount / expenseCount` 全部由同一批流水汇总，`balance = income − expense`，不使用 `v_project_fund` 的另一套口径。
- 待核对捐赠、待复核/待二签支出都不进入台账。

## 7 结项规则

```text
FUNDING ──已达标──> TARGET_REACHED ──> PENDING_SETTLE ──SETTLE──> SETTLED
    │
    └──未达标但已到截止日──> DEADLINE_REACHED ──> PENDING_SETTLE ──SETTLE──> SETTLED

PENDING_SETTLE ──SETTLE──> SETTLED
```

- 存在 `PENDING_REVIEW` 或 `FIRST_APPROVED` 支出时拒绝结项，返回 `40105`；
- 报告 20—10000 字，结余去向必填且 ≤255 字，附件 ≤10；
- 项目已有公示时拒绝重复提交；
- 公示金额取项目 `raised_amount` 与已复核支出合计，校验支出不得超过已筹；
- 写入 `project_settlement` 后项目置 `SETTLED`、`spent_amount=approved`，并写 `PROJECT_SETTLE` 审计；
- `GET /projects/{projectNo}/settlement` 与结项附件为匿名只读。
