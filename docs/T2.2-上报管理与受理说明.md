# T2.2 上报管理、受理与工单创建说明

## 1 接口

| 方法/路径 | 鉴权 | 说明 |
|---|---|---|
| `GET /api/v1/reports` | `ANIMAL_ADMIN` / `SYSTEM_ADMIN` | 上报列表；支持 `status`（逗号分隔）、`type`、`pointId`、`overdue`、`page`、`size` |
| `GET /api/v1/reports/{id}` | 登录 | 上报详情；`contact` 仅管理员或上报人本人可见 |
| `POST /api/v1/reports/{id}/accept` | `ANIMAL_ADMIN` | 受理并生成救助工单 |
| `PUT /api/v1/reports/{id}/close` | `ANIMAL_ADMIN` | 关闭无效上报，`reason` 必填 |

列表筛选口径：

- `overdue=true`：`status <> CLOSED` 且 `created_at < now - 24h`。
- `overdue=false`：`status <> CLOSED` 且 `created_at >= now - 24h`。
- 不传 `overdue`：不按 24 小时切片，仅按状态/类型/点位过滤。
- 排序：`created_at DESC`；`overdue` 由服务端按 24 小时计算，不落库。

## 2 受理

请求：

```json
{ "handlerId": 3001, "animalCode": "CAT-2026-001", "note": "已联系处置人" }
```

- `handlerId` 可不填，默认当前管理员；`animalCode` 可不填，默认沿用上报已关联的 `animal_id`。
- 仅 `PENDING` 上报可受理；已受理/已关闭回 30602。
- 工单状态走 `StateMachines.order()`：`PENDING --ACCEPT--> PROCESSING`，不写 if-else。
- 工单号 `RO + yyyyMMdd + 当日流水`，由 `OrderCodeGenerator` 基于 `seq_no` 行锁发号。
- `deadline_at = report.created_at + 24h`；`accepted_at = now`；`acceptor_id` 为当前管理员。
- 受理后上报状态同步置为 `PROCESSING`，并写 `sys_log`（`biz_type=RESCUE_ORDER`，`biz_id=orderNo`）。

响应：

```json
{ "orderNo": "RO20261121001", "reportNo": "RP20261121007",
  "reportStatus": "PROCESSING", "orderStatus": "PROCESSING",
  "deadline": "2026-11-22T10:31:00+08:00" }
```

## 3 关闭

请求：`{ "reason": "重复上报" }`

- 仅 `PENDING` 上报可关闭；原因去空格后不得为空，空原因 30401。
- 关闭后 `report.status=CLOSED`、`report.close_reason=reason`，写 `sys_log`。
- 已受理上报不通过本接口关闭，后续走工单 `CANNOT_DISPOSE` 或 `REVISIT_OK` 状态流转。

## 4 错误码

| 码 | 触发 |
|---|---|
| 30301 | 请求体/分页参数不合法 |
| 30303 | `status`/`type` 枚举非法 |
| 30401 | 关闭原因为空 |
| 30410 | 上报/档案不存在 |
| 30602 | 上报不是 PENDING、或工单状态机拒绝当前角色 |

## 6 本轮边界

1. **工单看板与流转接口未做**：`GET /orders`、`GET /orders/{no}`、`PUT /orders/{no}/status` 及时间线展示留到下一轮；本轮只保证受理能生成正确工单。
2. **学生进展通知未接**：受理后学生可通过上报详情看到 `PROCESSING` 与 `orderNo`，但站内消息要等 C 的消息通道；B 不直接写 `message` 表。
3. **关闭仅限 PENDING**：已受理上报的关闭/合并走工单状态机，避免一条上报既被受理又被直接关掉。
4. **超时扫描未做**：`TIMEOUT` 事件已在状态机表里，但每小时扫描任务属于 T2.3。
